一条消息进来，分身怎么接。

下面两段演示等比复刻 Nous 的两个真实入口：Mac 悬浮助手（浮在微信桌面版之上）和飞书 bot。所有判断、草稿、质检文案均为认知模型的真实输出记录，交互为模拟重放。

场景二 · 手机上把消息转发给飞书 bot对话重放 · 文案为 2026-09-01 真实输出
老板：你明天能加个班吗
不用急着回，晚点顺手回就行。压过来的活不紧急，别秒答应。 ⚠️ 你嘴上说今晚多干会儿，按你毛病多半是拖到半夜赶一点就睡——草稿把承诺压到今晚，别真拖。 可以这么回： 明天不行，我约了人。急的话我今晚多干会儿

用法就一步：把收到的消息转发（或粘贴）给 bot，可加「老板：」「同事：」这类关系前缀。

几秒后拿到三样东西：回不回的判断、可直接复制的草稿、质检警告——第三样是平台自带 AI 助手结构上给不了的。

真实链路：飞书长连接（官方 WSClient，无需公网 URL）→ 分身服务 → 飞书消息 API 回复。

bot 回复为生产日志原文，未润色。

同一个大脑，三个真实入口。

macOS · Swift 原生

悬浮助手（上面的场景一）

通知横幅自动感知或双击 ⌘C 召唤；非激活面板不抢焦点，「填入输入框」直达微信/钉钉聊天框。生产自用中。

飞书 · 官方开放平台

bot（上面的场景二）

手机上的入口。长连接模式绕开跨境 webhook 的 3 秒超时，全程官方 API。生产自用中。

产品终态的概念演示：跨平台消息聚合成一个通知中心。六条预设会话含多轮脚本，也可丢真实消息在线分析。

数据边界（主动交代）

  • 两段演示里的判断、草稿、质检文案均为认知模型 2026-09-01 的真实输出记录（场景二为生产日志原文），不是为页面编写的文案。
  • 界面为等比复刻的模拟重放：真实产品运行在本机（Mac 助手）与飞书客户端内，无法直接嵌入网页。
  • 准确率数据（行为预测 71%、模型理解 99%）出自项目验证记录，打分方式为确定性评分，非模型自评。
  • Web 沙盒是产品愿景的概念演示，与当前真实形态（悬浮助手 + bot）的关系在案例拆解中说明。
